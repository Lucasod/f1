## 6. Verification of Defect Candidates D01-D05

### D01 — Tool-name normalization: CONFIRMED

**Evidence:**
```typescript
// Line 199
return READ_LIKE_TOOLS.has(tool.toLowerCase());
```
`READ_LIKE_TOOLS` contains `"readFile"` (uppercase F). `"readFile".toLowerCase()` = `"readfile"` which is NOT in the set. Verified with Node.js:

- `has('readFile'.toLowerCase())` → `false`

**Impact:** A tool named `readFile` (exact case as listed) will never be recognized as read-like, so sensitive-path reads via `readFile` will NOT be blocked.

### D02 — POSIX character classes in JavaScript RegExp: CONFIRMED

**Evidence:** Lines 102-108 use `[[:space:]]` in RegExp constructor strings:
- Line 102: Connection string pattern `[^[:space:]/:@]+`
- Line 103: Password pattern `[[:space:]]*[:=][[:space:]]*`
- Line 104: API key pattern `[[:space:]]*[:=][[:space:]]*`
- Line 105: Generic secret pattern `[[:space:]]*[:=][[:space:]]*`
- Line 106: Authorization header pattern `[[:space:]]*[:=][[:space:]]*`
- Line 107: Cookie pattern `[[:space:]]*[:=][[:space:]]*`
- Line 108: Session id pattern `[[:space:]]*[:=][[:space:]]*`

JavaScript RegExp does NOT support POSIX character classes. `[[:space:]]` is interpreted as a literal character class containing `:`, `s`, `p`, `a`, `c`, `e` — NOT whitespace. Verified with Node.js: pattern `(password|passwd|pwd)[[:space:]]*[:=]` returns `false` for both `"password ="` and `"password="`.

**Impact:** All 7 patterns using `[[:space:]]` will fail to match whitespace-separated assignments (e.g., `password = "secret"`), causing under-detection of sensitive content.
