### Recommended architecture

**A. Wallet balance: Recalculated from transactions (ledger-derived)**
- Option 1 (cached): O(1) read, requires transactional updates, risk of drift, recovery needs reconciliation.
- Option 2 (recalculated): Always consistent, simpler recovery, O(n) read but n is bounded by transaction count per vendor.
- Recommendation: Recalculated as default; optionally cache with reconciliation. Given CD-030 defers this decision, recommend recalculated for MVP (simpler, always consistent, easier to audit). Cache can be added later.

**B. Transaction history: Minimum fields**
- id (ObjectId/uuid), walletId, type (enum), amount (decimal, signed), referenceId (uuid), referenceType (enum: OrderVendorGroup, Order, Refund, Payout), createdAt
- runningBalance (decimal, snapshot after transaction) — per CD-033 append-only and analysis schema
- metadata (object, optional) — for additional context
- No description field (derivable from type + reference)

**C. Running balance: Persisted per transaction**
- Each transaction stores runningBalance = previous + amount
- Enables O(1) latest balance read (last transaction) and audit trail
- Consistent with analysis_data_integrity.md schema

**D. Wallet ownership: One-wallet-per-vendor (simpler)**
- Wallet has ownerId (vendor id or "marketplace") + ownerType (vendor/marketplace)
- No wallet_id on Vendor (avoids migration); wallet is looked up by (ownerType, ownerId)
- Unique index on (owner_type, owner_id)
- Marketplace wallet uses ownerType="marketplace", ownerId="marketplace" (singleton)

**E. Persistence: MongoDB collections**
- wallets: { _id, owner_type, owner_id, balance (cached/optional), currency, last_transaction_id, updated_at } — unique (owner_type, owner_id)
- transactions: { _id, wallet_id, type, amount, running_balance, reference_id, reference_type, payment_id?, refund_id?, metadata, created_at } — indexes on (wallet_id, created_at), (reference_id, reference_type), (payment_id), (refund_id)
- Append-only: never update/delete transactions (CD-033)
- Use MongoDB sessions for atomic wallet+transaction updates

**F. API contract (minimum for T-1006)**
- GET /api/v1/wallets/me — get current vendor's wallet summary (balance, currency, last transaction)
- GET /api/v1/wallets/me/transactions — paginated transaction history (page, limit, type filter)
- GET /api/v1/wallets/:walletId (admin) — get any wallet by ID
- GET /api/v1/wallets/:walletId/transactions (admin) — paginated transactions for any wallet
- POST /api/v1/wallets/:walletId/adjustments (admin) — manual adjustment transaction

**G. Marketplace singleton: Not needed**
- Use ownerType="marketplace" with a well-known ownerId ("marketplace") instead of a separate configuration record
- Existing config mechanisms (env vars, config files) suffice for commission percentage

### Canonical transaction types (reconcile discrepancies)

Map to OpenAPI uppercase: SALE, COMMISSION, REFUND, PAYOUT, ADJUSTMENT
