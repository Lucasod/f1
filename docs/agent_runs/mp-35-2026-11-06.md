### Design choices (CR-002 durable recovery)
`ResilientAgentDelegationPort.delegateToCode` now:
1. Checks in-process `completedOps` (never repeat a completed operation).
2. Loads the checkpoint; if `lastCompletedAction === operationId` it returns the persisted `completedReport` without re-invoking the inner port — so non-idempotent ops are never replayed.
3. If the checkpoint claims completion but stores no report, it throws and refuses to replay (safe-fail rather than re-execute).
4. On success, persists the full `CodeExecutionReport` in the checkpoint under the explicit optional key `completedReport` (`ContinuityCheckpoint.completedReport?`, `continuity-checkpoint.ts:48`). Validation is backward-compatible: the field is optional, and when present it must be an object (`isValidCheckpoint`, `continuity-checkpoint.ts:62-68`). Checkpoints written before this field remain loadable.
5. On exhaustion/stop, writes a durable `on_exhaustion` checkpoint and throws (no infinite loop).

### Design choices (CR-003 / CR-004)
- CR-003: `writeCp` now appends each stage to an internal `stageHistory` array and writes `recentToolOutcomes` as the full sequence; `providerAttemptHistory` remains authoritative (`resilient-orchestration.ts:141-173`).

### Findings addressed (independent review: CORRECTIONS_NEEDED)

**CR-001 (MEDIUM, CONFIRMED) — `decide()` advances idle cycles when called before `nextCheckAt`.**
- Root cause: `decide()` (`idle-recovery.ts`) never consulted `due(now)`; when called while `nextCheckAt` was set and `clock.now() < nextCheckAt`, it still incremented `idleCycle` and recomputed `nextCheckAt` from `clock.now()`, compressing the 30/60/90/120/180m progression.
- Fix: after the lease fence and before any snapshot/mutation, if `nextCheckAt` is set and `!due(clock.now())`, return a non-advancing `IDLE` decision (`reason: 'not due yet'`) carrying the same `idleCycle`, `nextCheckAt`, `passCount`, and remaining `nextCheckInMs`, without mutating any counter or the schedule. Fence keeps precedence; when due, all existing behavior (reset/eligible-task/exhaustion) is unchanged.

**CR-002 (MEDIUM, CONFIRMED) — lease fence bypassed after reload when `claimedBy` persisted but `ownerId` not supplied.**
- Root cause: `loadSync` restores `claimedBy`/`schedulerActive` but not `ownerId`; the fence (`claimedBy && ownerId && claimedBy !== ownerId`) evaluated to false when `ownerId` was `null`, so a reloaded engine with `claimedBy='sched-A'` and `ownerId=null` called `decide()` without being fenced.
- Fix: fence now fails closed — `claimedBy && (!ownerId || claimedBy !== ownerId)` → `SAFE_STOP`. An owner reloading with the correct `ownerId` still proceeds (claimedBy matches); a competing owner (e.g. `sched-B`) is still fenced; explicit rebind via `claimMission(sameOwner)` restores `ownerId` and unblocks. `ownerId` remains instance identity (constructor-supplied), not restored from persisted state, so persistence alone cannot silently bind a reloaded engine.

Risk: `capturePayment` persists `paymentRepo.update(payment)` as `CAPTURED` (`payment.service.ts:229`) then separately calls `markCapturedOrderPaid` (`:231`) which reloads and updates order (`:238-246`). There is **no transaction boundary** across payment CAPTURED persistence and order PAID persistence. A crash/failure between `:229` and `:246`, or concurrent processing, can leave CAPTURED payment + `PENDING_PAYMENT` order (repair path exists via `capturePayment:208-211` and `isPaymentFinalized:394-397`, but repair is not atomic and depends on subsequent calls).
2. **Stale read-modify-write across service + repo (non-PAID and multi-entity):** Service methods read entities (`paymentRepo.findById`/`orderRepo.findById`), apply in-memory mutations/transitions, then write back (`update/save`) without compare-and-swap/version checks. Examples: `authorizePayment` reads payment+order then updates payment (`payment.service.ts:138-173`); `failPayment` updates payment, reads/updates order, restores stock in separate steps (`:273-325`); `refundPayment` updates payment then reads/updates order (`:336-361`). `MongoOrderRepository.save` uses conditional filter only for `PAID` transitions (`order.mongo.repository.ts:117-155`); **non-PAID order transitions have no conditional/version guard** (`:121,123-143` with unconditional `_id` filter and upsert except PAID path). A stale concurrent writer can overwrite newer state for non-PAID paths (MP-34 CR002 hypothesis).
3. **Duplicate webhook/`completeCheckoutPayment` interleaving:** `completeCheckoutPayment` checks terminal states and `PENDING` (`payment.service.ts:186-193`) but performs `authorizePayment` then `capturePayment` as separate calls without a shared atomic fence. Two deliveries could interleave around payment status reads/updates. Some idempotent returns exist (authorize same txn `:144-151`, capture already CAPTURED `:208-211`, order already PAID handling `:147-154`), but **payment repository updates are not shown to be conditional/idempotent by status+transaction** in service code; race window remains **UNVERIFIED** without concurrent execution proof.
4. **Lost update / overwrite of advanced state:** `markCapturedOrderPaid` reloads and only transitions if `PENDING_PAYMENT` (`:243-245`), catches `INVALID_STATUS_TRANSITION` and re-reads (`:251-264`). This mitigates regression for the PAID-repair path. However, `MongoOrderRepository` unconditional non-PAID saves (`order.mongo.repository.ts:121,142`) and service paths that update orders outside the PAID-conditional helper (`failPayment:298-302`, `refundPayment:360-361`) can still apply stale in-memory transitions against newer persisted state. `InMemoryOrderRepository` has limited PAID guard only (`order.domain.ts:867-871`), not general optimistic concurrency.
5. **Idempotent repair behavior vs completeness:** Repair exists for captured-payment/order-still-pending (`capturePayment:208-211`, `markCapturedOrderPaid`, `isPaymentFinalized:394-397`) and for already-terminal/duplicate cases in several methods. This is necessary but not sufficient to prove concurrency safety: idempotency handles repeated identical logical events; it does not by itself prevent stale concurrent writers from applying incompatible state transitions when updates are unconditional.
